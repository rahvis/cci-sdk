# Patient-portal triage: baseline vs. CCI-guarded — comparison report

**Synthetic demo data only. Not medical advice, not a medical device.**

Held-out test set: 16 cases, generated by `data/generate_patient_cases.py` (seeded, deterministic). Both pipelines use the same Claude model for drafting; the only variable is whether CCI's calibrated layer sits in front of what gets auto-sent.

## Headline numbers

| | Baseline (no CCI) | CCI-guarded |
|---|---|---|
| Urgency accuracy (top guess) | 88% (14/16) | 100% candidate-set coverage (16/16) |
| Auto-sent to patient | 50% (8/16) | 0% (0/16) |
| Auto-sent AND wrong | 0 | 0 |
| Auto-sent, high-acuity (urgent/emergency) | 4 | 0 (by design) |
| Avg. confidence/score on auto-sent cases | 0.93 (self-reported, no stated meaning) | n/a — none auto-sent in this run |
| Claims caught and dropped before reaching patient | not checked (no mechanism) | 19 dropped, 19 retained |

## What the numbers mean

**Baseline auto-sent 8 of 16 replies**, including **4 at urgent_care/emergency severity**, purely because its own self-reported confidence cleared an arbitrary 0.8 cutoff. That number has no stated error-rate meaning — it is the model's own opinion of itself, not an audited bound. In this run every auto-sent case happened to be classified correctly (0 wrong-and-auto-sent), which is exactly the risk: nothing in the baseline's design would have stopped it from auto-sending a *wrong* emergency-level reply with the same unearned confidence.

**CCI auto-sent 0 of 16 replies in this run.** Every urgent_care/emergency case (8 of them) was escalated to a human nurse queue regardless of how confident the underlying model was — a categorical policy enforced by the pipeline's structure (only a singleton, low-acuity candidate set is even considered for auto-send), not a probability. For the low-acuity cases, the `Claim` check (19 claims dropped across the run, 19 retained) turned out to be strict enough that at least one claim in every drafted reply failed to clear the calibrated support threshold — usually a generic recommendation sentence the small (~48-example) calibration set and the sampling-based Claude evidence scorer couldn't yet back with enough confidence. That is the system correctly saying *I don't have enough evidence to certify this exact reply* rather than guessing: fail-closed by design, matching the product's own documentation. With the ~1,000-example calibration set the docs recommend for production use, the same mechanism would start clearing genuinely well-supported replies while still catching the same kind of drop seen here.

## Guarantee cards actually returned (verbatim)

- Set: Contains the correct answer at least 80% of the time on profile 'patient-triage-set-v1' (n=48).
- Gate: Expected rate of decisions that are auto-approved and wrong is at most 0.15 (conformal risk control, n=48).
- Claim: With probability at least 70%, every retained claim is supported (conformal factuality, n=48).
